Moodbar — Maquettes & conception UX

Ce document présente les 3 écrans du MVP et les choix d'expérience utilisateur qui les sous-tendent. Les aperçus web et borne ci-dessous réutilisent directement le CSS du prototype (moodbar-frontend/style.css) : ce ne sont pas des captures d'écran figées mais un rendu fidèle du même code. Le dashboard, lui, est une application Streamlit dynamique — l'aperçu ci-dessous est donc un wireframe qui reproduit sa structure réelle (moodbar-dashboard/app.py), pas un rendu pixel-perfect.

Choix UX

  • 3 boutons uniques, aucune autre action possible : le vote se fait en un geste, sans réflexion.
  • Aucune authentification ni saisie : l'anonymat encourage la sincérité du vote.
  • Feedback immédiat (son + message affiché, ici #feedback) : transforme un simple clic en interaction gratifiante.
  • Le message se réinitialise après 4s pour que l'écran reste net pour le prochain passage.
  • Accessible sur poste fixe, tablette ou smartphone sans installation (page web standard).

Choix UX

  • Boutons et texte agrandis par rapport à la version web : pensé pour un usage tactile, à distance, dans un lieu de passage (hall, cafétéria...).
  • Même code que l'application web (script.js partagé) : seul data-source="iot" change, pour distinguer l'origine du vote en base.
  • La mention « Borne simulée » est volontairement visible : transparence vis-à-vis du jury sur l'absence de matériel physique (contrainte budget, voir REQUIREMENTS.md).
  • Aucune barre de navigateur visible en usage réel (mode kiosque plein écran du navigateur).

Choix UX

  • 3 métriques en tête : lecture immédiate de la répartition globale, sans interprétation nécessaire.
  • Filtre de période (sélecteur de dates) + granularité jour/semaine/mois : permet de zoomer sur un événement précis (période d'examens, etc.).
  • Graphique d'évolution en courbe : les pics/anomalies (ex. baisse de moral) sautent visuellement aux yeux.
  • Table de détail en bas de page : accès aux données brutes pour vérification, sans être la première chose vue.
  • Bouton « Actualiser » + cache de 30s : équilibre entre fraîcheur des données et charge sur la base, sans complexité de websocket.
